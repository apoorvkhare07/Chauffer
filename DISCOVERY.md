# Discovery agent

Planning update, 21 October 2026: [the next recommendation architecture](docs/RECOMMENDATION_ARCHITECTURE.md) proposes relevant personal memory across chats, a shared task planner and specialist recommendation judgement. The builder explicitly requested that new chats retain relevant understanding of the person. The session-only behaviour described below records the current implementation, not the intended future memory policy.

Discovery turns a shopper's intent into verified merchant options. It is the first specialist in the shared agent flow. Explicit wardrobe shopping requests now receive an additional styling check against available saved clothes.

The current flow uses Convex Agent (`shoppingAI.ts`) for conversation planning, `aiDecision.ts` plus `discoveryPolicy.ts` and `discoveryQuestions.ts` for enforced decisions, `discoveryWorkflow.ts` for the sequence, `liveDiscovery.ts` for retrieval and `ranking.ts` for the shortlist. Retrieval remains responsible for merchant evidence; the model never invents products, prices or stock.

## Shopper decisions

- Preserve category, audience, maximum budget, size and explicit constraints during refinement. Clear item-specific brand/attributes when switching categories unless restated.
- Ask one question at a time. Missing category/budget/size comes first. Choose the highest-priority missing detail for this item: intended use for sneakers, fit for jeans/trousers, occasion or pattern for clothing, then style/colour/material/brand as relevant. Do not force a brand-first sequence. Ask at most one optional clarification before a broad search, and show results after the answer or skip. A focused request searches directly. Post-result questions refine the existing search; track offered fields so declined/unanswered questions do not repeat. A selected brand is a hard constraint; “any” records an explicit open choice. Multiple named brands prompt which to search first. New brands can be supplied in text.
- Default spending preference is 60–100% of the stated ceiling. Within that band, rank by stated style evidence and proximity to 80% of budget, with store variety. Cheaper alternatives follow when the band has fewer candidates, with a clear note. This is a preference, not a minimum restriction, quality score or instruction to spend the maximum. “Cheapest options” switches to lower-priced ranking; “best within budget” switches back.
- Include a selected brand in merchant terms; suppress optional style terms that can over-constrain a brand search, retaining explicit hard constraints. Match brand against the row's brand evidence or title, rejecting inspired-style substitutes. Brand presence does not verify authenticity or product quality.
- Guest preview stays one search. It follows budget ranking but does not block on optional brand clarification; follow-up requires sign-in. Without a supplied budget it uses the existing broad ceiling and lower-priced ordering, not an inferred spending target.
- After results, explain the spending range and ask one relevant brand, occasion or feedback question. Never claim a wider search than the bounded catalogues read.

## Shared agent flow

One conversation planner owns the shopper reply and confirmed requirements. The workflow searches once, then optionally asks the styling specialist to assess possible combinations with confirmed available wardrobe items. Only explicit current-chat requests such as “jeans with my wardrobe” enable that check. Short follow-ups retain this scope; reset/new search clears it; “don't use my wardrobe” disables it. Ordinary searches do not load wardrobe/style data or make a styling model call. The existing standalone outfit picker remains separate.

Styling receives merchant evidence, known owned IDs, saved style preferences and a bounded current-session brief. It cannot fetch products, change requirements or invent owned pieces. Returned references are checked against the exact supplied products/items. The screen shows possible pairings, not a visual colour, size-stock or body-fit guarantee. A failed styling check leaves real product results intact. Missing inventory asks the shopper to add available clothes. Exact private snapshots are checked before publishing and when displaying results; wardrobe/style changes hide old pairings and request a fresh check.

The versioned format and its limits are documented in [AGENT_HANDOFF.md](docs/AGENT_HANDOFF.md). This is the first connected discovery/wardrobe/styling journey, not a general autonomous agent system or a trained quality score.

Question buttons carry the exact field/value chosen by the shopper, bypassing a second model call. Free-text replies still use the discovery agent. A skip starts retrieval without inventing the missing attribute; “no more questions” disables further optional questions for that item. Occasion words only improve ranking when merchant text supplies evidence (for example training/walking/formal); they are not suitability or comfort guarantees. Bounded merchant queries include confirmed occasion/style terms with broad fallback retaining hard constraints.

Within the spending band, explicit fit/pattern/style and occasion evidence come before store variety. Unknown/nonmatching preferences remain fallback; do not insert a straight-fit pair just to add another store when relaxed-fit matches exist. When needed to fill the shortlist with evidence matches, allow up to six per store; ordinary searches retain the normal source cap. Hard constraints still apply to every option.


## Goal and session boundaries

Discovery succeeds when the shopper explicitly confirms the shortlist is useful. Returning product cards only advances the conversation to refining. “These work for me” (or an equivalent explicit message) confirms the current shortlist without saving, purchasing or changing account preferences. A further refinement reopens discovery; new search/reset starts exploring again. Do not infer success from a result count, save, click or absence of feedback.

For jeans, after fit is known and results exist, ask colour before generic occasion questions. Colour answers preserve category, size, budget, fit, brand and other current requirements. Short model replies cannot silently clear unmentioned current requirements, must-haves or feedback; explicit “any fit/colour” can relax that field.

A session means the current chat until new search/reset, including reloads of that chat. Context contains only its bounded history, confirmed requirements, taste, shown/rejected URLs and references. New chats do not automatically import learned taste from profile/past chats. Explicit account size/budget/audience/language settings remain defaults, and saved records/history are retained. Stored wardrobe/styling context is supplied only when the current chat explicitly requests it. Convex Agent cross-thread search remains off. Earlier current-session information survives in structured state even when the bounded message window no longer contains the original wording.

## Coherent refinement replies

Keep the original request visible, show the latest shopper direction separately, and retain both its acknowledgement and the finished-result reply. Confirm changes from the previous structured requirements/taste instead of relying only on generated prose. Show confirmed occasion/style/fit/pattern alongside budget/size/brand/colour. An active question owns the answer buttons; do not replace them with generic search actions. AI chat questions return structured field/choices, including the named-brand clarification. Clicking an answer updates that field while retaining the other confirmed current-chat details. Older products remain labelled Previous picks while awaiting clarification or updating, so they are not presented as results of an unanswered question. Keep custom text and skip available.

The expanded pool has twenty configured destinations. Ten additional readers and their evidence limits are documented in [STORE_EXPANSION.md](docs/STORE_EXPANSION.md). An attempted source is not a guaranteed integration: blocked/readability failures stay unavailable, readable catalogues without verified matches stay no_matches. Uniqlo remains direct-only/unavailable when blocked; its unsuccessful browser trial does not enable additional paid recovery. H&M and Nykaa browser trials have not established reliable production prices; their automatic recovery remains off. Keep the existing six-card shortlist and browser-call limits.

## Refinement retrieval — 21 October 2026

Seen products are history, not rejected products. Answering a question or refining a request re-fetches the catalogue with all current constraints and allows previously shown matching picks. Explicitly rejected URLs stay excluded. Requests for another batch continue to exclude shown URLs. The optional conversation `excludeShown` flag records that distinction; old records remain readable.

Single-page direct readers and browser recovery use core merchant terms (category, audience, colour, fabric, chosen brand and explicit must-haves). Occasion, fit and other optional style terms guide ranking rather than shrinking those single-page searches. Flipkart and Amazon retain their bounded focused-plus-broad direct retrieval. Existing browser-call limits and strict product checks are unchanged. Broader terms do not restore blocked store access or guarantee six matches.

## Gated recommendation route (21 October 2026)

Authenticated web turns selected by `RECOMMENDATION_V2_OWNERS` use the new shared-task workflow described in [the architecture record](docs/RECOMMENDATION_ARCHITECTURE.md). The planner interprets the current task; discovery gathers a wider evidence pool; product understanding inspects bounded images; recommendation ranks with relevant personal memory; a separate final check and code validation precede publication. Ordinary refinements retain matching shown products. Current requests override memory; gifts do not use the shopper's own preferences or wardrobe.

Development and production are enabled for signed-in web requests as of 21 October 2026. Guest requests and accounts outside the flag continue through the established path. See TESTING_LEDGER.md for actual test evidence rather than treating the design acceptance list as completed.

## Zyte discovery and try-on handoff — 22 October 2026

When server-only `ZYTE_API_KEY` is configured, shared discovery uses Zyte's India `productList` extraction on broad store search URLs. The first response uses HTTP extraction; unreadable or unfinished stores can receive one browser-rendered extraction in background workers. At most four provider calls run together per search phase, across up to twenty stores. A store can therefore receive two calls (HTTP plus browser), with no automatic retries or Browserless cascade. Responses remain bounded to 2 MB. See the temporary-pool section below for timing bounds. Without the key, the established direct-reader/browser route remains available.

Only valid same-store product links with INR prices and trusted image URLs enter matching. Merchant colour/title and fabric evidence still undergo existing hard-constraint checks, image inspection and ranking; retrieval never invents missing colour, fabric, size stock or suitability. Missing extraction remains unavailable. Readable nonmatches are distinct from unavailable stores. Extracted records are not automatically recommendations, and sparse merchant descriptions can still limit matches.

Signed-in result cards and their details expose Try on. The fitting room uses the selected message's existing product image, checked against the owner's conversation on the server, without a save or a second product extraction. The shopper supplies one photo and consent, can switch between that result set's pictured products, and return to results without clearing the photo. Leaving discovery, starting a new chat, refreshing, or Clear session clears the photo; photos/previews remain page state only. Gemini continues to generate previews. Development verification is recorded in TESTING_LEDGER.md; this does not claim production rollout.

## Temporary discovery pool (22 October 2026)

Zyte listing retrieval retains up to ten normalized priced products per store for thirty minutes, scoped to the owner’s current conversation session and listing URL. Each turn reapplies constraints and excludes shown/rejected URLs. Matching cached candidates bypass store planning and retrieval; expired, changed-query or explicit refresh requests retrieve again. Failed reads are cached for two minutes. Cleanup runs every ten minutes. First retrieval uses Zyte HTTP extraction with four concurrent calls, six seconds per call and twelve seconds overall. It stops early once two stores provide at least eight candidate products. Remaining/unreadable stores use up to four scheduled browser-recovery workers, each bounded to forty-five seconds and eighteen seconds per store, filling the same pool after the first response. Successful first results do not trigger a second blocking search. Empty first results may wait up to twelve seconds for the existing recovery pool, without launching duplicate retrieval. This is not a whole-response latency guarantee.

Merchant product paths can supply missing brand/colour facts; search query parameters never do. Structured brand names and material are preserved. Missing colour may reach image inspection, but publication requires a positive visual match; known mismatches remain rejected. Size stock is not verified.

## Colour preference and recovery correction — 22 October 2026

Colour is now a ranking preference by default: exact colour-family matches precede nearby alternatives (for example blue before purple/teal; purple before blue/pink). Publication uses the colour observed in the product image and labels alternatives explicitly; unrelated colours and uncertain image evidence remain excluded. “Only blue” or equivalent explicit wording sets `colourStrict`; subsequent short refinements preserve it until changed. The requested brand, audience, category and budget remain constraints. Explicit “any brand” removes the previous brand.

Purple includes lavender, lilac, violet, mauve and plum. The store pool now chooses ten relevant candidates from at most sixty extracted records, rather than truncating the first ten before checking suitability. A second retrieval excludes every candidate already assessed on that turn; rejected cached products cannot short-circuit the wait for fresh recovery evidence. First-response timing limits are unchanged.

## Inspection variety — 22 October 2026

Before the existing eight-image check, retain hard constraints and colour priority, then explicit style evidence. Within equal preference tiers, defer repeated design titles or the same image path until different candidates have been considered. Title similarity only changes inspection order; it does not establish product identity, delete variants, or prove visual similarity. Distinct candidates retain their original relative order. This avoids spending most image slots on repeated models without adding retrieval, image or model calls. The final recommendation still judges suitability and may return fewer than six.

## Browse catalogue on Discover — 24 October 2026
A separate shared public-merchandise catalogue supports browsing below the search. Eighteen fixed store/category/brand queries return at most ten pictured, priced products each. Direct readers precede Zyte HTTP extraction, then one bounded rendered extraction. Two workers fill a shared Convex cache; no AI calls, private chats, user preferences or photos are part of these refreshes. Authenticated visits reserve expired work once across visitors. Successful batches refresh after six hours on demand; failed reads cool down for30minutes, retain previous observations for at most48hours, and do not claim no stock. Prices are dated observations, not checkout guarantees. The sixteen featured brand icons stay fixed even when a brand currently has no products. Marketplace names never become brand icons.
The initial grid interleaves stores; filters and Show more use that same pool without another search. Server-held catalogue references authorize private saves, affiliate links and temporary try-on. Arbitrary client product facts are rejected; saved pieces remain owner-bound. The existing AI chat search is unchanged.

### Brand and merchant identity — 25 October 2026
Catalogue products carry separate brand and store values. Store comes from the validated product URL. Brand comes from structured product metadata, an explicit product-brand URL segment, or a known own-label store; search query text never supplies it. Brand aliases share one identity across stores. Targeted brand batches reject unrelated products. Existing rows are normalized on read; fresh batches persist normalized brand/store evidence. Fixed brand icons filter across merchants, and Store remains a separate filter. Public catalogue retrieval adds Nike, Adidas, Levi’s, Mango, ONLY, Vero Moda, Jockey, Roadster, HRX and FableStreet batches. Two refresh chains run in two-source chunks, with a twelve-minute reservation covering the bounded eighteen-source sweep. No extra retrieval runs when filtering cached products.

### Basket handoff — 25 October 2026
Catalogue and owned chat results can be added to tryOnBasket through server-held references. The server resolves source ownership and product/photo evidence, deduplicates the same URL, and enforces eight picks per owner. Independent basket records preserve trusted public product snapshots when catalogue refreshes or a new chat removes the original context. No savedProducts entry or media storage is created. Basket try-on and merchant links resolve the owner-bound snapshot. The frontend keeps one original compressed portrait in page memory and calls the existing Gemini renderer sequentially; errors are visible per piece, provider-busy failures stop the remaining queue, and retry is deliberate. Backend preview locking, consent and merchant image validation still apply. Account data export includes basket picks.
